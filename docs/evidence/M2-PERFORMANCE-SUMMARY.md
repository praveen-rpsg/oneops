# M2.4 — Performance Summary (Dependency Graph)

**Milestone:** M2.4 — Performance Validation & Operational Hardening
**Date:** 2026-07-22
**Environment:** golang:1.25 + PostgreSQL 16 (containerized), arm64
**Unit under test:** `postgres.GraphRepo` recursive-CTE traversal (M2.2), unchanged.

All numbers below are reproduced from the committed integration tests/benchmarks
(`internal/store/postgres/graph_perf_test.go`, `graph_bench_test.go`). No schema,
API, or traversal-logic changes were made in M2.4.

---

## 1. Acceptance result

| Metric | Target | Measured | Verdict |
|---|---|---|---|
| `RecursiveDependencies` p95 @ 10k nodes / 30k edges | **< 50 ms** | **0.71 ms** | ✅ PASS (70× margin) |

Source: `TestGraphPerf10kAcceptance` — 1000 block-root traversals.

---

## 2. Latency percentiles (RecursiveDependencies)

| Dataset | roots | p50 | p95 | p99 | avg | max |
|---|---|---|---|---|---|---|
| 10k nodes / 30k edges (blocks) | 1000 | 617 µs | **705 µs** | 987 µs | 628 µs | 1.52 ms |
| 50k nodes / 150k edges (blocks, stress) | 5000 | 671 µs | **807 µs** | 1.32 ms | 696 µs | 6.17 ms |
| wide star, reach = 4999 | 50 | 4.32 ms | **4.88 ms** | 5.28 ms | 4.38 ms | 5.28 ms |

Sources: `TestGraphPerf10kAcceptance`, `TestGraphPerf50kStress`, `TestGraphPerfReachableSize`.

**Key finding — cost tracks the *reachable subgraph*, not the total graph.** 10k→50k
(5× the table) barely moves p95 (705 µs → 807 µs) because index seeks on
`ix_edge_from`/`ix_edge_to` keep per-hop cost flat; what grows the number is the
*reachable* set (wide star reaching 4999 nodes ≈ 4.9 ms). Realistic config graphs
have small, bounded dependency subtrees, so production p95 is sub-millisecond.

## 4. Documented limitation & recommendation (not a defect)

**Deep single-path chains are O(depth²).** The traversal's cycle guard carries the
visited path as a per-row array; a depth-D chain copies an O(D) array O(D) times.
Evidence: Deep(1500) = 114 ms vs Linear(800) = 33.7 ms ≈ (1500/800)² × 33.7 ≈ 118 ms.

This is **not a defect and not a blocker**: the M2.4 acceptance target is met for
realistic (sparse, shallow, bounded) config-graph topologies, where p95 < 1 ms.
It is recorded as a **future recommendation** (deferred, requires its own story):
if very deep dependency chains become common, replace the array-based cycle guard
with PostgreSQL's native `CYCLE` clause or a bounded-depth traversal. No change is
made in M2.4 per the "do not add unless it fixes a genuine defect" rule.

---

## 5. Allocation / GC behaviour

Allocations scale with the *reachable node count and path length*, not total graph
size (Wide reaches 4000 nodes → 12k allocs; blocks reach ≤10 → far fewer). Growth is
linear and bounded per request; no unbounded retention was observed. CPU/heap
profiles are generated by:

```bash
go test ./internal/store/postgres/ -tags=integration -run=^$ -bench=BenchmarkGraphScale10k \
  -cpuprofile=cpu.out -memprofile=mem.out
go tool pprof -top cpu.out
```
