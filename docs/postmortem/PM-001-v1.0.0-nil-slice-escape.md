# PM-001 — Blameless Postmortem: two default API paths returned HTTP 500 in v1.0.0

| | |
|---|---|
| **Incident** | `POST /v1/admin/webhooks` (no filters) and `POST /v1/admin/webhooks/{id}/replay` (time-window) returned `HTTP 500` |
| **Release** | `v1.0.0` (`9032021`, tagged 2026-07-22 23:51) |
| **Detected** | 2026-07-23 11:14 — manual runtime probing during an unrelated review |
| **Resolved** | 2026-07-23 11:37 (`a808544`), released `1.0.1` at 12:57 (`78adc1b`) |
| **Severity** | **Sev-3.** Two documented default paths unusable. **No realized customer impact** — the platform has no deployment and no users; impact was potential, not actual |
| **Related** | EDR-001 (the engineering decision) — this document covers *escape*, not the fix |

This is a blameless review. The repository has **one author and no second party available for review**; that is a property of the engineering system's current staffing, not a personal failing, and it is treated as a system input throughout.

---

## 1. Executive Summary

Two documented default behaviours were unusable in GA. A nil Go slice encodes as SQL `NULL`, an explicit `NULL` bypasses a column `DEFAULT`, and three `text[] NOT NULL DEFAULT '{}'` columns rejected it.

**The controls that would have caught this existed and were correct. They had never been executed.** The two integration tests that fail on the defect were written and committed *in the release commit itself* and have never passed. The CI pipeline that would run them has never run at all, because the repository has **zero remotes configured**.

The defect was found ~11h46m after the tag, by a person running the API by hand and reading the log during an unrelated review. That is the weakest detection method available, and it was the only one operating.

## 3. Detection

**How it was found:** manual runtime probing during a review of an unrelated change. Not by a test, not by an alert, not by CI.

**Could existing systems have detected it earlier? Yes — one of them was designed to, and would have.**

| Control | Existed? | Would it have caught this? | Why it didn't |
|---|---|---|---|
| **Integration tests** | **Yes** | **Yes — proven.** Both fail deterministically on the defect | **Never executed before the tag.** They were authored in the same commit as the defect |
| CI (6 jobs) | Defined in `.github/workflows/ci.yml` | Yes — the `integration` job runs exactly these tests and fails on skip | **Zero remotes configured.** Triggers are `pull_request` and `push: [main, release/**]`; with no remote, GitHub Actions has never run a single job |
| Unit tests | Yes, and they ran | **No** | Every test supplied *populated* slices. Lines were covered; the nil *value* was never exercised |
| Code review | Process defined in CONTRIBUTING | Possibly | **1 author, 0 merge commits, 0 PRs.** No second party available |
| Release checklist | Yes | Yes — the box was already `[ ]` | **Advisory, not blocking.** An unchecked box did not stop the tag |
| Observability | Partial | **No** | The 500 emitted one `INFO http_request` line with no cause; 51 of 52 `mapError` sites discard the error |

**The decisive fact: the test that detects this defect shipped in the same commit as the defect, and has never passed.**

## 4. Root Cause Analysis

**Primary (technical) cause.** pgx encodes a nil slice as SQL `NULL`; an explicit `NULL` bypasses the column `DEFAULT`; the constraint rejects it. The schema and the Go type system were each internally correct and disagreed at the boundary between them. Nil is *semantically meaningful* at all three call sites — "all events", "time-window mode" — so the natural value is the failing one.

**Contributing causes.**

1. **A 152-file release commit.** Every other commit in the project is 7–8 files; `9032021` is **19× larger than the next largest** and introduced four subsystems plus release hardening atomically. A change of that size cannot be meaningfully reviewed, and leaves no increment at which a smaller failure would have surfaced.
2. **Zero elapsed time between commit and tag.** Both are stamped 23:51. No verification window existed by construction.
3. **Tests authored alongside the code they test, in the same commit, never run.** Writing the test does not exercise it.
4. **Coverage measured lines, not values.** The defective statements were covered; the nil input was not. Coverage percentage could not have revealed this.

**Organizational cause — where the "why" chain terminates.**

> **The engineering system's controls are fully specified and largely non-operational.** Six controls are defined (unit, integration, CI, review, checklist, observability). At the moment of the GA tag, **one was operating** (unit tests). The others existed as configuration, documentation, or intent.

This is not a discipline problem. The controls were designed carefully — the CI workflow even fails the build if an integration test is *skipped*, which is a sophisticated guard. It has simply never run.

**False leads.**

- `nullTime`, sitting directly above the defective line, handles the analogous nil-time case **correctly** — making nil-handling look considered. Proximity, not evidence.
- The GA release note *"CI now runs PostgreSQL-backed integration tests (fails on skip)"* is **true as configuration** and was never a false claim. It describes the workflow file, not an execution.
- Four unused compose services (NATS, Redis, OpenSearch, MinIO) found nearby — unrelated.

**Unknowns.** Benchmark regression status (suite exceeds a 10-minute budget; not measured). Whether `gitleaks`/`trivy` would pass today — not re-run; the dependency set is byte-identical to `v1.0.0`, so the surface cannot have changed, but that is inference.

| Gate | Status at GA | Evidence |
|---|---|---|

| CI | **Never executed** | 0 remotes; workflow requires push/PR to GitHub |

**It reached production because the only operating gate was the one gate that could not see it.**

## 8. Lessons Learned

**We believed** the GA release had been verified — the checklist existed, the CI workflow was sophisticated, the integration tests were written, and the release notes described all of it accurately.

**We discovered** that writing a control is not operating a control. Six were defined; one was running. The integration suite that detects this defect was committed *in the same commit as the defect* and had never been executed. The CI that would have run it has never run at all, because the repository has no remote.

**This escaped because** the only gate actually operating — unit tests — was structurally incapable of seeing it: every test supplied populated slices, so the defective lines were covered while the failing value was never passed. Coverage reported success over code that had never been given the input that breaks it.

**Future releases will** not be tagged until a CI execution record exists and every checklist box is checked, with an unchecked box treated as a blocking unknown rather than a note. Zero elapsed time between commit and tag is now itself a finding.

**The engineering system improved because** the integration suite is green for the first time in the repository's measured history — so it is now a usable signal rather than known-noise; `atlas migrate validate` and the rollback path have been genuinely exercised rather than assumed; and the gap between *defined* and *operating* controls is now measured and tracked, which is the difference this postmortem is meant to make.
